# Маруська Арена — архитектура

Онлайн-дурак для реальных игроков Telegram внутри экосистемы бота Маруська.
Сервер решает всё: раздачу, чей ход, законность каждой карты, итог и деньги.
Клиент показывает состояние и отправляет намерения.

## 1. Что уже есть в репозитории и что из этого следует

| Факт | Решение |
|---|---|
| Бот написан на **Python** (aiogram 3 + aiohttp) и работает одним процессом на Railway: long polling плюс веб-сервер на `PORT` для Mini App «Рыбалка» и «Крокодил». | Арену **не встраиваем** в Python-процесс. Это отдельный Node/TypeScript-сервис в папке `arena/`, отдельный сервис на Railway. Бот продолжает работать как раньше. |
| В `public` уже есть таблицы `users`, `transactions`, `user_achievements` (алмазы, достижения бота) со своей структурой. | Все таблицы арены живут в **отдельной схеме `arena`** той же PostgreSQL. Ни одна таблица бота не меняется, конфликтов имён нет. Миграции Prisma и их служебная таблица `_prisma_migrations` тоже лежат в `arena`. |
| Проверка Telegram initData уже написана в `webapp/server.py`, `fishing_api.py`. | Та же схема HMAC повторена в `apps/api/src/telegram/initData.ts` с проверкой срока и тестами на подделку. |
| Алмазы 💎 бота хранятся в `public.user_profiles.coins` и меняются через `SELECT … FOR UPDATE`. | На первом этапе у арены **своя валюта** (фишки для ставок, монеты, алмазы-резерв) со своим журналом. Мост «алмазы бота ↔ арена» делается отдельно, через идемпотентный обмен (этап 5). Так ошибка в арене не может испортить экономику бота. |
| `Dockerfile` бота делает `COPY . .` | Добавлен корневой `.dockerignore` с `arena/`: образ бота не растёт и не тащит Node-код. |
| `test_imports.py` импортирует все `.py` рекурсивно. | Папка `arena/` и `node_modules` исключены: там встречаются чужие `.py`. |

### Замечания к ТЗ

* **Команда `/игра` в меню невозможна.** Telegram допускает в командах только латиницу, цифры и `_`. Поэтому в меню бота стоит `/game` (и `/durak`), а «/игра» ловится как текст. В личке также срабатывают «игра», «играть», «дурак». В группах бот откликается только на явные фразы вроде «в дурака», чтобы не засыпать чат кнопками и не перехватывать отгадки «Крокодила».
* **Восемь «режимов» — это на самом деле четыре пары переключателей:** Подкидной/Переводной, Все/Соседи (кто подкидывает), Честная/С шулерами, Классика/Ничья (исход, когда последний отбился последней картой). Комната хранит все четыре значения, а фильтр лобби ищет по любому из них. «С шулерами» пока отклоняется сервером (`MODE_NOT_SUPPORTED`).
* **Deep link `t.me/<бот>?startapp=…`** открывает только *главное* Mini App бота (BotFather → Bot Settings → Configure Mini App). Если арена будет не главным приложением, ссылка должна иметь вид `t.me/<бот>/<short_name>?startapp=game_<id>`. `roomDeepLink()` в `@arena/shared` строит оба варианта.
* **Ставки до 10M и «баланс».** Валюта виртуальная и не выводится. Любая продажа фишек за Telegram Stars и тем более вывод денег превращают игру в азартную с юридической точки зрения. До такого решения монетизация — только косметика.
* **Название.** Предлагаю «**Маруська Арена**»: оно не привязано к одному дураку, и под ним можно добавлять другие игры. Название задаётся в одном месте (`index.html`, заставка).

## 2. Схема взаимодействия

```
 Telegram-клиент
   │  /game → кнопка «🎮 Играть» (web_app) или t.me/<бот>/<app>?startapp=game_<id>
   ▼
 Mini App (React, apps/web)  ──HTTPS──►  Arena API (Fastify, apps/api)  ──►  PostgreSQL, схема arena
   │   initData → POST /api/auth/telegram  │  проверка HMAC, upsert user,          (users, wallets, transactions,
   │   ◄── session token (HS256, 24 ч)     │  бонус новичку (идемпотентно)          rooms, games, game_moves…)
   │                                       │
   └──WSS /ws?token=… (этап 2)────────────►│  Room/Game manager  ──►  Redis
                                           │   · game-engine (чистые функции)       (живое состояние комнат,
                                           │   · таймеры ходов                        presence, pub/sub между
                                           │   · журнал ходов в game_moves            инстансами, локи)
                                           │
 Бот Маруська (Python) ◄──────────────────┘  outbox notifications / Bot API sendMessage
   · кнопка «Играть», приглашения, итоги партий
```

* **Идентичность.** Единственное доказательство личности — подписанная Telegram строка `initData`. Сервер проверяет подпись токеном бота, срок (`INIT_DATA_MAX_AGE_SECONDS`), создаёт или обновляет пользователя и выдаёт короткий токен сессии. Никакой `userId` от клиента не принимается.
* **Один источник правды.** Состояние партии хранится только на сервере (память процесса + снапшот в Redis). Клиент получает `PlayerView`: свою руку, число карт у соперников, стол, козырь, число карт в колоде и список разрешённых действий.
* **Бот ↔ арена.** Арена кладёт уведомления в таблицу `notifications` (outbox). Доставлять их может сама арена через Bot API тем же `BOT_TOKEN` (`sendMessage` не конфликтует с long polling бота) или бот через `/internal/*` с `INTERNAL_API_SECRET`. Приглашения в комнату — это ссылки `startapp=game_<roomId>`, которые Mini App разбирает после авторизации (`AuthResponse.startParam`).

## 4. Игровое ядро (`packages/game-engine`)

Файлы: `Card`, `Deck`, `Rules`, `GameState`, `Actions`, `TurnManager`, `AttackManager`, `DefenseManager`, `TransferManager`, `GameEngine`, `PlayerView`, `Scoring`.

```ts
applyAction(state, playerId, action, now) → { ok: true, state, events } | { ok: false, error }
applyTimeout(state, now)                  → ход «за игрока», когда истёк таймер
legalActions(state, playerId)             → { attack[], defend{card→targets}, transfer[], take, pass }
toPlayerView(state, viewerId)             → то, что можно отправить этому игроку
settle(result, players, stake, rake%)     → выплаты
```

`applyAction` — чистая функция: входное состояние не меняется, а отклонённый ход ничего не применяет наполовину. Случайность приходит извне (`Random`): на сервере криптографическая, в тестах с зерном. Поэтому партию можно воспроизвести по сохранённой колоде и журналу ходов.

**GameState:** `gameId, version, status, phase (attack|defense|taking|finished), rules, players[{id, seat, hand, status, place}], deck, trump{suit, card}, table[{attack, defense, by}], discard, attacker, defender, currentPlayer, boutLimit, boutNumber, passed[], turnDeadline, finishOrder, winner, loser, result`.

Правила, заложенные сейчас (их можно поменять в `Rules.ts` и `TurnManager.ts`):

* 36 карт, по 6 на руки, козырь — последняя карта колоды, первым ходит младший козырь.
* В первом отбое не больше 5 карт, дальше не больше 6 и не больше, чем карт у защитника на начало отбоя.
* Подкидывать можно карты достоинств, уже лежащих на столе. «Все» — подкидывают все, «Соседи» — атакующий и второй сосед защитника.
* Перевод: пока ничего не отбито и все карты одного достоинства, при условии что следующий игрок сможет ответить на все карты. В партии на двоих перевод возвращает атаку обратно.
* «Беру»: соперники ещё могут подкинуть, после чего защитник забирает стол и пропускает ход.
* Добор: главный атакующий, затем остальные по часовой стрелке, защитник последним.
* Конец: последний игрок с картами — дурак. Если последнюю карту отбили последней картой: «Ничья» — ничья, «Классика» — дурак тот, кто подкинул последнюю карту.
* Выход из партии — поражение: вышедший становится дураком, партия заканчивается.
* Таймаут: атакующий ходит младшей картой, защитник берёт, подкидывающие пасуют.

Тесты: отдельные правила (атака, защита, подкидывание, лимиты, режимы, перевод, концовки, таймауты, скрытие карт, расчёт) и **800 случайных полных партий** на 2–6 игроков. В каждом ходе проверяется, что все 36 карт на месте, дублей нет, лимиты соблюдены и партия всегда заканчивается.

## 5. База данных (Prisma, схема `arena`)

`users` (telegram_id UNIQUE) · `profiles` · `wallets` (user, currency) UNIQUE, `CHECK balance >= 0` · `transactions` (idempotency_key UNIQUE, `CHECK balance_after = balance_before + amount`) · `rooms` · `games` (initial_deck для аудита) · `game_players` · `game_moves` (append-only, UNIQUE (game, seq)) · `game_results` · `friends` (двунаправленно) · `friend_requests` · `items` · `user_items` · `achievements` · `user_achievements` · `tournaments` · `tournament_players` · `notifications` (outbox для бота).

### Деньги (`services/ledger.ts`)

Баланс меняет только `Ledger.post()`:

1. Внутри одной транзакции БД выполняется условный `UPDATE wallets SET balance = balance + x WHERE … AND balance >= -x`. Строка блокируется до коммита, поэтому двойная трата невозможна.
2. В той же транзакции пишется строка `transactions` с `balance_before/after`, типом, источником и `idempotency_key`.
3. Повтор с тем же ключом, даже одновременный, откатывается на UNIQUE и получает в ответ первую запись.
4. Ни один маршрут не принимает сумму от клиента: суммы берутся только из правил сервера (ставка комнаты, расчёт `settle`).

Интеграционный тест: 25 одновременных списаний по 1000 с баланса 10 000 — ровно 10 проходят, 15 получают `INSUFFICIENT_FUNDS`, итоговый баланс 0. Восемь одновременных одинаковых выплат зачисляются один раз.

Ставки (этап 5): при старте партии — `GAME_STAKE:<gameId>:<userId>` для всех игроков одной транзакцией; в конце — `GAME_PAYOUT:<gameId>:<userId>` по `settle()`; при сбое сервера — `GAME_REFUND`. Комиссия берётся только из ставки дурака.

## 6. WebSocket-протокол (`packages/shared/src/protocol.ts`)

Один сокет на клиента: `/ws?token=<session>`. Сообщения клиента проверяются zod-схемой; у каждого может быть `rid`, и сервер отвечает `ACK` или `ERROR` с тем же `rid`.

Клиент → сервер: `PING, LOBBY_SUBSCRIBE, LOBBY_UNSUBSCRIBE, ROOM_WATCH, READY, RECONNECT{roomId, lastVersion}, PLAY_CARD{gameId, card, target?}, TRANSFER, TAKE_CARDS, PASS, LEAVE_GAME`.

Сервер → клиент: `LOBBY_SNAPSHOT, ROOM_CREATED, ROOM_UPDATED, ROOM_REMOVED, ROOM_JOINED, ROOM_LEFT, GAME_STARTED, GAME_STATE (персональный PlayerView), GAME_EVENTS (CARD_PLAYED, CARD_TRANSFERRED, CARDS_TAKEN, ROUND_FINISHED, PLAYER_TURN, CARDS_DRAWN — только количество…), GAME_FINISHED, PLAYER_CONNECTED, PLAYER_DISCONNECTED{graceUntil}, PLAYER_RECONNECTED, ERROR, PONG`.

Каждый игрок получает **свой** `GAME_STATE`. Карты соперников, порядок колоды и содержимое отбоя с сервера не уходят (это проверяет тест `player view`). `version` растёт с каждым принятым ходом: клиент отбрасывает устаревшие состояния, а после переподключения запрашивает снимок.

Реконнект: при обрыве игрок помечается `disconnected`, соперники получают `PLAYER_DISCONNECTED` со сроком ожидания, партия продолжается по таймерам. Вернувшись, клиент отправляет `RECONNECT` и получает полный `GAME_STATE`.

## 7. Масштабирование

* Движок не хранит ничего в глобальном состоянии, а партия — это данные. Её можно сериализовать в Redis и продолжить на другом инстансе.
* Каждая комната закреплена за одним инстансом (владельцем) через Redis-лок `room:<id>:owner`. Лобби и присутствие хранятся в Redis, изменения рассылаются через pub/sub. «Серверы» (Алмаз, Рубин…) уже записываются в каждую комнату, так что позже их можно разнести по отдельным пулам инстансов.
* PostgreSQL получает только редкие записи: создание комнаты, старт и конец партии, журнал ходов пачками, деньги. Горячая часть работает в памяти и Redis.
